Every design system I've worked in exists twice. There's the Figma file, where
it's laid out on a board — grouped, labelled, everything visible at once, easy
to reason about as a system. And there's the code, where the same system is a
folder of files you open one at a time.

The two drift apart immediately. They have to: they're separate artifacts kept
in sync by hand, and the moment either side moves, the other is wrong. What I
want is the board, with the code as the source of it. Not a picture of the
system — the system.

That's what Pane is going toward. An infinite canvas where every frame is a
real `.tsx` file on disk, arranged spatially the way you'd arrange it in Figma,
live.

## The canvas is organised like a design system

Not like a file tree. You group frames and name the groups, drag and resize
them, and they sit behind the components the way sections do in Figma. There's
a tokens file you open from the toolbar, and a light/dark switch for the whole
workspace, because a system has to hold up in both.

The components underneath are plain files. Git works, imports work, and an
agent editing them gets the same live board I'm looking at.

## The part that had to work first

A board of components is only worth having if changing the system changes the
board. So that's the mechanic I built to prove out.

`Button.tsx` exports `ButtonRoot`, and every shared decision lives in one string
at the top of it:

```
const base =
  'inline-flex items-center justify-center gap-1.5 rounded-md border ...'
```

`Toolbar.tsx` uses `ButtonRoot` five different ways on purpose — icon-only
toggles, disabled, loading, danger, a primary with icon and label. Five cases
that break differently.

Change `gap-1.5` to `gap-2` and both frames move while you're still typing. If
it ruins the icon-only toggles, you find out in the same second, on the board,
next to everything else it touched — not three steps later in an app.

Two components is a small proof. It's the smallest one that actually
demonstrates propagation, which is why the demo workspace is that and not
thirty.

## What it costs to host

Locally this leans entirely on a Vite dev server and HMR. There isn't one on
Vercel, so the deployed demo does something else: the editor posts the files
into each frame, which transpiles them in the browser with Sucrase and
re-renders, with Tailwind's browser JIT covering classes you type that didn't
exist yet.

It's a real fallback, not the same thing. Edits live in memory, so a refresh
throws them away. I'd rather say that here than let someone find out by losing
work.

## Where it is

The canvas primitives are in — groups, tokens, themes, scaffolding new
components — and the propagation loop works. What's in the repo is a seed of
the board, not a board. That's the distance left, and it's the interesting
part: the idea only pays off at the scale of a whole system, and I've proved
it at the scale of a button.
