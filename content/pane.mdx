Every component tool I've used is built on isolation. You open a component, you
see that component, you judge that component. It's a clean idea and it answers
the wrong question.

Because the thing you actually need to know, the moment you touch anything
shared, is: what did that just do to everything else? A design system isn't a
collection of components. It's the set of relationships between them — and
isolation is structurally incapable of showing you a relationship. The answer
only exists in the aggregate.

So you change a padding value on the one button every other button is built
from, and then you go looking. Open the toolbar. Open the form. Open the empty
state. Somewhere in there is the place it broke, and you'll find it in review,
or you won't.

## Latency decides what you're willing to try

The second thing is quieter and I think it matters more.

A feedback loop with a delay in it doesn't just slow you down. It changes what
you attempt. If seeing a change costs a save, a rebuild and a navigation, you
stop making speculative ones — you only make the changes you already believe
in. Which means the exploratory half of design, the part where you try the
version you're pretty sure is wrong, quietly stops happening. You converge on
your first instinct and call it a decision.

Pane is an attempt to make that cost approximately zero, so that trying the
wrong thing is free and you find out something.

## The tool should be disposable

Components stay ordinary `.tsx` files on disk. Not exported, not synced, not
living in a proprietary format with a bridge back to reality.

This is the part I'd defend hardest, and it isn't a technical preference. A
tool that owns your work makes leaving expensive, and a tool you can't leave
stops having to earn its place. Files on disk means git works, imports work,
your editor works and coding agents work without knowing Pane exists — and if
Pane turns out to be a bad idea, you delete it and lose nothing.

The measure of a tool like this is how little it costs to abandon.
